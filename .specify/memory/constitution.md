# libread Constitution

libread は、本を借りずに図書館の館内で読む人が、近隣の複数図書館のうち
「今日開館していて、読みかけの本を手に取って続きを読める館」を知るためのサービスである。

## Core Principles

### I. シンプルさ優先 (YAGNI)

- 実装は、現時点で仕様（spec.md）に書かれた要件を満たす最小の構成で行わなければならない (MUST)。
- 将来の拡張を見越した抽象化・汎用化・設定項目を、具体的な利用箇所が2つ以上生じる前に
  導入してはならない (MUST NOT)。
- サーバー（Go）の外部ライブラリは、標準ライブラリで妥当なコード量に収まらない場合にのみ
  追加する (MUST)。
- 画面（TypeScript）は React と Vite を前提とする。それ以外の実行時の依存は、ブラウザの
  標準 API と React で妥当なコード量に収まらない場合にのみ追加する (MUST)。
  開発時だけの依存（型チェック・lint・テストの道具）はこの限りではない。
- 外部ライブラリを追加するときは、plan.md にその理由を記録する (MUST)。
- 複雑さを伴う設計判断は、plan.md の Complexity Tracking に「より単純な代替案を
  採らなかった理由」とともに記録しなければならない (MUST)。

**Rationale**: 個人規模のプロジェクトであり、保守できる人数が限られる。
使われないコードはそれ自体が負債になる。画面の依存は増えやすく、更新や脆弱性の対応の手間が
そのまま保守の負担になる。

### II. テストファースト (NON-NEGOTIABLE)

- すべての機能変更・バグ修正は、失敗するテストを先に書き、失敗を確認してから実装する
  Red-Green-Refactor サイクルで行わなければならない (MUST)。サーバーと画面の両方に適用する。
- 画面では、利用者から見える振る舞い（表示する内容、取得中・失敗・古い情報などの状態の
  切り替え、操作の結果）をテストの対象とする (MUST)。色や余白などの見た目の細部は対象外とする。
- バグ修正には、そのバグを再現するテストを必ず含める (MUST)。
- 外部の図書館データ取得（Web ページ・API）は、記録済みのレスポンスを使った
  テストで検証しなければならない (MUST)。テストは実ネットワークに依存してはならない (MUST NOT)。
  画面のテストも、サーバーへの通信を記録済みまたは定義済みの応答で差し替えて行う (MUST)。
- 日付・時刻に依存するロジック（開館判定など）は、現在時刻を注入可能にしてテストする (MUST)。
- サーバー・画面いずれかのテストが失敗した状態でマージしてはならない (MUST NOT)。

**Rationale**: 開館日や所蔵状況の判定ミスは、利用者に無駄足を踏ませるという
直接的な損害になる。画面が「不明」や「古い情報」を正しく示せなければ、判定が正しくても
同じ損害になる。テストが判定と表示の正しさを担保する唯一の手段である。

### III. 型安全

- ドメイン上の概念（図書館ID、書誌ID、所蔵状態、開館時間など）は、素の `string` や
  `int` ではなく専用の型として定義しなければならない (MUST)。
- 状態を表す値（貸出可・貸出中・館内のみ・不明など）は、定義済みの型付き定数として
  表現し、未知の値を受け取った場合は明示的に「不明」として扱う (MUST)。
- Go では、`any` / `interface{}` は、JSON デコードなど外部境界で不可避な場合を除き
  使用してはならない (MUST NOT)。境界で受け取った値は、ただちに型付きの値へ変換する。
- TypeScript では strict モードを有効にし、`any` を使用してはならない (MUST NOT)。
  サーバーから受け取った値は `unknown` として受け、検証してから型付きの値へ変換する (MUST)。
- サーバーと画面の間のデータ形式は、契約（contracts/）として文書で定義し (MUST)、
  サーバーと画面の両方のテストで契約に従っていることを確かめる (MUST)。
- エラーは握りつぶしてはならず (MUST NOT)、Go では `fmt.Errorf("...: %w", err)` で文脈を
  付けて返すか、その場で明示的に処理する。画面では、失敗を利用者に見える形で表示する。
- Go の `go vet` と `staticcheck`、TypeScript の型チェックと lint が警告を出さない状態を
  維持しなければならない (MUST)。

**Rationale**: 複数図書館のデータ形式の違いを型で吸収することで、
誤ったデータがドメインロジックへ流れ込むのを防ぐ。サーバーと画面の境界も外部境界であり、
同じ扱いをしなければ、型の食い違いがそのまま誤った表示になる。

### IV. 情報の正確性と鮮度

- 利用者に表示する所蔵状況・開館情報には、取得元（図書館名・データソース）と
  取得日時を必ず併記しなければならない (MUST)。
- 取得に失敗した、または鮮度の許容範囲を超えたデータを、最新の情報として
  表示してはならない (MUST NOT)。その場合は「不明」または「古い情報」と明示する。
  画面に表示し続けている結果も、判定した時刻を併記し、鮮度の許容範囲を超えたら
  「古い情報」と明示する (MUST)。
- 開館判定は、通常の開館時間に加えて臨時休館・特別整理期間を考慮しなければならない (MUST)。
  これらを確認できない場合は、その旨を表示する。
- 「読める」かどうかの判定はサーバー側だけで行い、画面で判定ロジックを重ねて実装しては
  ならない (MUST NOT)。画面はサーバーの判定結果を表示する。
- 確定できない状態を「読める」と推測で表示してはならない (MUST NOT)。

**Rationale**: このサービスの価値は「今日行けば読める」という判断の信頼性にある。
誤った「読める」表示は、何も表示しないことより有害である。判定が2か所にあると、
どちらかだけが直されて結果が食い違うおそれがある。

## 技術的制約

- 言語は次のとおりとする (MUST)。
  - サーバー（判定・外部データソースへの問い合わせ・利用者データの保存）: Go。
    `go.mod` に記載したバージョンの標準ツールチェーンでビルドできること。
  - ブラウザで動く画面: TypeScript（React、Vite でビルド）。
- コードは、Go は `gofmt` で、TypeScript はリポジトリで定めた整形ツールで整形されて
  いなければならない (MUST)。
- 外部データソース（図書館 Web サイト・API）への配慮:
  - 各ソースの利用規約・robots.txt に従う (MUST)。
  - 同一ソースへのリクエストにはレート制限を設け、結果をキャッシュして
    不要な再取得を避ける (MUST)。
  - 外部データソースへの問い合わせはサーバーから行い、画面から直接行ってはならない (MUST NOT)。
- 秘密情報:
  - API キーなどの秘密情報をリポジトリにコミットしてはならない (MUST NOT)。
    環境変数や実行環境の秘密情報の置き場所から読み込む。
  - 秘密情報を画面に渡してはならない (MUST NOT)。画面のビルド成果物にも含めてはならない。
- クラウドでの実行:
  - 利用者データ（読みかけの本・メモ・利用図書館・開館情報）の表示・変更と、
    外部データソースへの問い合わせは、本人であることを確認した相手にだけ許可しなければ
    ならない (MUST)。確認していない相手には、利用者データの有無も分からないようにする。
  - 通信は HTTPS だけで受け付けなければならない (MUST)。
- 利用者の読書状況（読みかけの本など）は個人情報として扱い、
  サービスの機能に必要な範囲を超えて収集・送信してはならない (MUST NOT)。

## 開発ワークフロー

- 機能開発は Spec Kit のフロー（`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`）に従う (SHOULD)。小さな修正はこの限りではない。
- plan.md の Constitution Check では、本書の各原則への適合を確認しなければならない (MUST)。
  違反がある場合は Complexity Tracking に正当化を記録する。
- マージ前の品質ゲート: すべて通ること (MUST)。
  - サーバー: `gofmt`、`go vet`、`staticcheck`、`go test ./...`
  - 画面: 整形の確認、型チェック（strict）、lint、テスト
  - 具体的なコマンドは plan.md と quickstart.md に定義し、1つのコマンドでまとめて実行できるようにする。

- 改定は、変更内容と理由をこのファイルの Sync Impact Report に記録したうえで行う。

- 仕様・計画・タスク・コードレビューの各段階で、本書への適合を確認する (MUST)。
