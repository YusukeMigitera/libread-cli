# libread Constitution

libread は、本を借りずに図書館の館内で読む人が、近隣の複数図書館のうち
「今日開館していて、読みかけの本を手に取って続きを読める館」を知るためのサービスである。

## Core Principles

### I. シンプルさ優先 (YAGNI)

- 実装は、現時点で仕様（spec.md）に書かれた要件を満たす最小の構成で行わなければならない (MUST)。
- 将来の拡張を見越した抽象化・汎用化・設定項目を、具体的な利用箇所が2つ以上生じる前に
  導入してはならない (MUST NOT)。
- 外部ライブラリは、標準ライブラリで妥当なコード量に収まらない場合にのみ追加する (MUST)。
  追加時は plan.md にその理由を記録する。
- 複雑さを伴う設計判断は、plan.md の Complexity Tracking に「より単純な代替案を
  採らなかった理由」とともに記録しなければならない (MUST)。

**Rationale**: 個人規模のプロジェクトであり、保守できる人数が限られる。
使われないコードはそれ自体が負債になる。

### II. テストファースト (NON-NEGOTIABLE)

- すべての機能変更・バグ修正は、失敗するテストを先に書き、失敗を確認してから実装する
  Red-Green-Refactor サイクルで行わなければならない (MUST)。
- バグ修正には、そのバグを再現するテストを必ず含める (MUST)。
- 外部の図書館データ取得（Web ページ・API）は、記録済みのレスポンスを使った
  テストで検証しなければならない (MUST)。テストは実ネットワークに依存してはならない (MUST NOT)。
- 日付・時刻に依存するロジック（開館判定など）は、現在時刻を注入可能にしてテストする (MUST)。
- `go test ./...` が失敗した状態でマージしてはならない (MUST NOT)。

**Rationale**: 開館日や所蔵状況の判定ミスは、利用者に無駄足を踏ませるという
直接的な損害になる。テストが判定の正しさを担保する唯一の手段である。

### III. 型安全

- ドメイン上の概念（図書館ID、書誌ID、所蔵状態、開館時間など）は、素の `string` や
  `int` ではなく専用の型として定義しなければならない (MUST)。
- 状態を表す値（貸出可・貸出中・館内のみ・不明など）は、定義済みの型付き定数として
  表現し、未知の値を受け取った場合は明示的に「不明」として扱う (MUST)。
- `any` / `interface{}` は、JSON デコードなど外部境界で不可避な場合を除き使用してはならない
  (MUST NOT)。境界で受け取った値は、ただちに型付きの値へ変換する。
- エラーは握りつぶしてはならず (MUST NOT)、`fmt.Errorf("...: %w", err)` で文脈を付けて返すか、
  その場で明示的に処理する。
- `go vet` と `staticcheck` が警告を出さない状態を維持しなければならない (MUST)。

**Rationale**: 複数図書館のデータ形式の違いを型で吸収することで、
誤ったデータがドメインロジックへ流れ込むのを防ぐ。

### IV. 情報の正確性と鮮度

- 利用者に表示する所蔵状況・開館情報には、取得元（図書館名・データソース）と
  取得日時を必ず併記しなければならない (MUST)。
- 取得に失敗した、または鮮度の許容範囲を超えたデータを、最新の情報として
  表示してはならない (MUST NOT)。その場合は「不明」または「古い情報」と明示する。
- 開館判定は、通常の開館時間に加えて臨時休館・特別整理期間を考慮しなければならない (MUST)。
  これらを確認できない場合は、その旨を表示する。
- 確定できない状態を「読める」と推測で表示してはならない (MUST NOT)。

**Rationale**: このサービスの価値は「今日行けば読める」という判断の信頼性にある。
誤った「読める」表示は、何も表示しないことより有害である。

## 技術的制約

- 言語は Go とし、`go.mod` に記載したバージョンの標準ツールチェーンでビルドできること (MUST)。
- コードは `gofmt` で整形されていなければならない (MUST)。
- 外部データソース（図書館 Web サイト・API）への配慮:
  - 各ソースの利用規約・robots.txt に従う (MUST)。
  - 同一ソースへのリクエストにはレート制限を設け、結果をキャッシュして
    不要な再取得を避ける (MUST)。
  - API キーなどの秘密情報をリポジトリにコミットしてはならない (MUST NOT)。
    環境変数などから読み込む。
- 利用者の読書状況（読みかけの本など）は個人情報として扱い、
  サービスの機能に必要な範囲を超えて収集・送信してはならない (MUST NOT)。

## 開発ワークフロー

- 機能開発は Spec Kit のフロー（`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`）に従う (SHOULD)。小さな修正はこの限りではない。
- plan.md の Constitution Check では、本書の各原則への適合を確認しなければならない (MUST)。
  違反がある場合は Complexity Tracking に正当化を記録する。
- マージ前の品質ゲート: `gofmt`、`go vet`、`staticcheck`、`go test ./...` が
  すべて通ること (MUST)。

## Governance

- 本 Constitution は、プロジェクト内の他のすべての慣行・ガイドラインに優先する。
- 改定は、変更内容と理由をこのファイルの Sync Impact Report に記録したうえで行う。
  既存の仕様・計画に影響する場合は、その移行方針も併記する (MUST)。
- バージョンはセマンティックバージョニングに従う:
  - MAJOR: 原則の削除、または後方互換性のない再定義
  - MINOR: 原則・セクションの追加、またはガイダンスの実質的な拡張
  - PATCH: 意味を変えない文言修正・明確化
- 仕様・計画・タスク・コードレビューの各段階で、本書への適合を確認する (MUST)。
