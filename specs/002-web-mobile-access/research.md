# Research: スマートフォンのブラウザから使える libread（Web 化）

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

001 の research（[R1〜R10](../001-readable-libraries-today/research.md)）は、所蔵状況・書誌・祝日の取得元、
判定、鮮度、外部サービスへの配慮について、そのまま引き継ぐ。ここでは Web 化で新たに決めることだけを書く。
番号は 001 と区別するため W を付ける。

## W1. 実行環境（クラウド）

- **Decision**: Google Cloud の Cloud Run（東京リージョン `asia-northeast1`）で、コンテナを1つ動かす。
  - 最小インスタンス数 0（使われていない間は停止する）、最大インスタンス数 1。
  - コンテナ1つに、Go のサーバーとビルド済みの画面（静的ファイル）を入れる。
- **Rationale**:
  - 本人確認に Google アカウントを使う（spec Clarifications）ので、同じ Google のアカウントで運用をまとめられる。
  - 使われていない間は課金されず、無料枠で収まる見込み（spec Assumptions「無料枠または月数百円」）。
  - Go の単一バイナリは起動が速く、停止状態からの起動は数秒で済む（SC-102 の30秒以内）。
  - 最大インスタンス数を 1 にすると、利用者データの読み書きを1つのプロセスの中だけで直列化できる（W3）。
    利用者は1人なので、1インスタンスで足りる。
- **Alternatives considered**:
  - 常時起動の VM（Compute Engine e2-micro の無料枠）: 停止状態からの起動はないが、OS の更新や HTTPS 証明書の
    管理を自分で行う必要があり、保守の負担が大きい（原則 I）。
  - 画面だけを静的ホスティング（Firebase Hosting など）に分ける: 配信先が2つになり、デプロイ手順と
    クロスオリジンの扱いが増える。1つのコンテナで同一オリジンにすれば CORS は要らない。

## W2. 本人確認（FR-110・FR-111）

- **Decision**: サーバーが Google の OpenID Connect（OAuth 2.0 の認可コードフロー）を自分で実装する。
  1. `GET /auth/login` で `state`（ランダム値。短時間の Cookie に入れる）を付けて Google の認可画面へリダイレクトする。
     要求するスコープは `openid email` だけ。
  2. `GET /auth/callback` で `state` を照合し、認可コードを Google のトークンエンドポイントへ TLS で直接送って ID トークンを受け取る。
  3. ID トークンの `iss`（`https://accounts.google.com` か `accounts.google.com`）、`aud`（自分のクライアント ID）、
     `exp`、`email_verified = true`、`email`（設定した本人のアドレスと一致）を確かめる。
     トークンエンドポイントから TLS で直接受け取った ID トークンは、署名の検証を省略できる
     （OpenID Connect Core 1.0 §3.1.3.7）。そのため、JWT のライブラリや公開鍵の取得は要らない。
  4. 本人なら、サーバーの秘密鍵で HMAC-SHA256 の署名をしたセッション Cookie を発行する。
     中身は「発行日時・有効期限（30日）・セッション世代番号」。本人以外なら Cookie を発行せず、本人以外として扱う。
- リダイレクト URI は `LIBREAD_PUBLIC_ORIGIN` + `/auth/callback`。ブラウザで開くオリジンごとに、OAuth クライアントへ登録する
  （ローカルの 8080 番と 5173 番、本番の Cloud Run の URL。quickstart「前提」）。
- セッション Cookie: `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`、有効期限30日（FR-111）。
- 全端末の確認の取り消し（FR-111）: サーバーに保存した「セッション世代番号」を1つ進める。
  それより古い番号の Cookie はすべて無効になる。取り消しを行った端末も、ログインし直しになる。
- 本人以外への応答（FR-110、Constitution「利用者データの有無も分からないようにする」）:
  確認できない要求には、`/api/` 以下のどの URL にも同じ `401` と同じ本文を返す。データの有無や件数で応答を変えない。
- CSRF 対策: 状態を変える要求（`POST`・`PUT`・`PATCH`・`DELETE`）は、`Origin` ヘッダーが自分のオリジンと
  一致するときだけ受け付ける。`SameSite=Lax` と合わせて、他のサイトからの書き換えを防ぐ。
- 秘密情報（Google のクライアントシークレット、セッションの署名鍵）は Secret Manager に置き、
  Cloud Run の環境変数として渡す。画面には渡さない（FR-113）。
- **Rationale**: 標準ライブラリ（`net/http`、`crypto/hmac`、`crypto/rand`、`encoding/json`）だけで作れる（原則 I）。
  30日の省略と全端末の取り消しを、仕様どおりに自分で制御でき、テストで確かめられる（原則 II）。
- **Alternatives considered**:
  - Identity-Aware Proxy（IAP）で Cloud Run の前段に Google ログインを置く: アプリ側の実装は要らないが、
    セッションの有効期間と全端末の取り消しを仕様どおりに制御できない。ローカルでの動作確認やテストで
    本人確認を再現できない。
  - `golang.org/x/oauth2` や `google.golang.org/api/idtoken` を使う: 依存が増えるわりに、
    認可コードの交換は HTTP の POST 1回で済み、署名の検証も W2-3 のとおり要らない。
  - Firebase Authentication: 画面側に SDK が入り、実行時の依存が増える（Constitution 原則 I の画面の基準）。

## W3. 利用者データとキャッシュの保存（FR-112）

- **Decision**: Cloud Storage のバケットを Cloud Run のボリュームとしてマウントし（Cloud Storage FUSE）、
  001 と同じファイル形式で保存する。
  - 利用者データ: `<マウント先>/data/data.json`（001 の形式。data-model.md）
  - 本人確認の状態: `<マウント先>/data/auth.json`（セッション世代番号）
  - キャッシュ: `<マウント先>/cache/`（`holdings.json`・`holidays-YYYY.json`。001 と同じ）
  - サーバーの中で、利用者データの「読み込み → 変更 → 書き込み」を1つのミューテックスで直列化する。
    変更はすべて「最新のデータを読み、1つの操作を当てて書く」形にする。
    2つの端末からほぼ同時に保存しても、他の本や図書館のデータは失われない（spec Edge Cases）。
    同じ本のメモを同時に書き換えた場合は、後から保存した内容が残る。
- **Rationale**:
  - 001 の `internal/store` をそのまま使える。データベースもクラウド用の SDK も要らない（原則 I）。
  - 最大インスタンス数が 1 なので（W1）、プロセス内のミューテックスだけで書き込みの競合を防げる。
  - データは数十件で、1回の読み書きは数 KB。
  - Cloud Storage のオブジェクトは丸ごと書き換わるため、書き込みの途中で読まれても壊れたファイルにはならない。
- データの保全: Cloud Storage の耐障害性に任せる。バックアップ・書き出し・復元は作らない（spec Assumptions）。
- デプロイ中の例外（受け入れる制約）: 最大インスタンス数はリビジョンごとの上限なので、新しいリビジョンへ切り替える短い時間は、
  古いリビジョンと新しいリビジョンが同時に動くことがある。その間に2つの端末から保存すると、片方の変更が失われるおそれがある。
  利用者は1人で、自分がデプロイした直後に保存しなければ起きないので、「デプロイの最中は保存しない」ことを運用の約束とし、仕組みは作らない（原則 I）。
  自動デプロイ（W13）で、利用者の知らないうちにデプロイが走るようになったら、この判断を見直す（世代番号での楽観ロック。下の Alternatives を参照）。
- **Alternatives considered**:
  - Firestore: 無料枠はあるが、001 の保存形式とは別の形式とクライアントライブラリが必要になる。
  - Cloud Storage の JSON API を直接呼び、世代番号で楽観ロックする: 複数インスタンスでも安全になるが、
    最大インスタンス数 1 では要らない。認証トークンの取得なども含めてコードが増える。
  - Cloud SQL: 月額の固定費がかかり、規模に対して過剰。

## W4. サーバーと画面のあいだの通信（FR-101〜FR-107、FR-104）

- **Decision**: 同一オリジンの JSON の HTTP API にする（[contracts/http-api.md](./contracts/http-api.md)）。
  - 検索（`GET /api/check`）は、すべての本の所蔵状況がそろうまで待ってから、結果をまとめて1回で返す（FR-104）。
    カーリルへの問い合わせ全体の上限は 001 と同じ8秒（001 R7）なので、応答は10秒以内に返る（SC-102）。
  - 画面は、応答を待つあいだ「取得中」とだけ表示する。
  - サーバーと画面のどちらの側でも、送り合うデータの形を型で定義し、契約に従っているかをテストで確かめる（原則 III）。
- **Rationale**: 途中の結果を送らないと決めたので（spec Clarifications）、逐次の送信（Server-Sent Events や WebSocket）
  も、ジョブを登録して状態を問い合わせる仕組みも要らない（原則 I）。
- **Alternatives considered**: 検索をジョブにして、画面から状態を問い合わせる。所蔵状況の取得は8秒で打ち切るので、
  1回の要求で待っても Cloud Run の要求タイムアウト（既定300秒）に十分収まる。

## W5. 表示する文言と判定の置き場所（FR-102、Constitution 原則 IV）

- **Decision**: 「読める」の判定、館の並び順、開館状態・所蔵状況の表示文言（「開館前 09:00〜19:00」「在架（貸出可）」など）は、
  サーバー（Go）で作って API で返す。画面は、受け取った値と文言を並べて表示するだけにする。
  - 001 の `internal/cli/format.go` にある文言を作る関数は、新しいパッケージ `internal/present` に移す。
  - 画面が自分で判断するのは、表示している結果の基準時刻から30分を超えたかどうか（FR-105「古い情報」）だけ。
    これは「読める」かどうかの判定ではなく、表示の鮮度の判定である。
- **Rationale**: 文言まで1か所にまとめると、001 の CLI と同じ結果になること（SC-103）を Go のテストだけで確かめられる。
  画面に判定や文言の対応表を重ねて持つと、片方だけ直されて食い違うおそれがある（原則 IV）。

## W6. 画面の構成（Constitution 技術的制約・原則 I）

- **Decision**:
  - TypeScript（strict）＋ React 19 ＋ Vite でビルドする。Node.js は 22 LTS。
  - 実行時の依存は `react` と `react-dom` だけにする。
  - 画面の切り替えはルーターのライブラリを使わず、URL のハッシュ（`#/`・`#/books`・`#/libraries`）で3つの画面を切り替える。
  - API の応答は `unknown` として受け、自分で書いた検証関数で型付きの値に変換する（原則 III）。
    スキーマ検証のライブラリ（zod など）は使わない。
  - スタイルは素の CSS 1ファイル。画面幅 360px を基準にし、横スクロールを出さない（FR-115）。
- 開発時だけの依存（Constitution 原則 I の例外）:
  - 型チェック: `typescript`（`tsc --noEmit`）
  - lint: `eslint`、`typescript-eslint`、`eslint-plugin-react-hooks`
  - 整形: `prettier`
  - テスト: `vitest`、`jsdom`、`@testing-library/react`、`@testing-library/user-event`
  - バージョンは `package-lock.json` で固定する。
- **Rationale**: 画面は3つで、ルーターや状態管理のライブラリを入れるほどの複雑さはない。
  検証関数は API の型が十数個なので、手で書いても妥当な量に収まる。
- **Alternatives considered**: React Router（3画面には過剰）、zod（実行時の依存が増える）、Tailwind CSS（ビルド設定と依存が増える）。

## W7. 画面のテスト（Constitution 原則 II）

- **Decision**:
  - Vitest と Testing Library で、利用者から見える振る舞いを確かめる。
    例: 取得中の表示、結果の表示、失敗と再試行、30分を超えた結果の「古い情報」、削除前の確認、401 のときの再ログインの案内。
  - サーバーへの通信は、`fetch` を差し替えて、contracts の例と同じ形の応答を返す。実ネットワークに接続しない。
  - 現在時刻は、Vitest の偽のタイマーで固定する。
  - 色や余白などの見た目の細部はテストしない。
  - 画面幅 360px で横スクロールが出ないことは、quickstart の手順で実機またはブラウザの開発者ツールで確かめる（自動テストにはしない）。
- **Rationale**: E2E テストは必須にしないと決めた（Constitution 1.1.0 の改定時の判断）。

## W8. 001 の CLI の廃止とデータの取り込み（FR-117・FR-118）

- **Decision**:
  - `POST /api/import` で、001 の `data.json` の中身をそのまま受け取る。001 と同じ読み込み処理で検証する。
  - 取り込めるのは、クラウド上の読みかけの本と利用図書館がどちらも0件のときだけ（「一度だけ」、FR-118）。
    それ以外は `409` を返し、何も変更しない。
  - 検証に1か所でも失敗したら、何も保存しない。
  - 取り込みが済んだら、`cmd/libread` と `internal/cli` を削除する。
    001 の受け入れシナリオのテスト（`internal/cli/check_test.go` など）は、同じデータと時刻を使う
    API のテストに書き直してから削除する（SC-103）。
- **Rationale**: 取り込みの画面は1回しか使わないので、画面にファイル選択を1つ置くだけにする。
  形式の変換を作らずに済むよう、001 の保存形式をそのまま受け付ける。

## W9. 外部サービスへの配慮（001 R9 の見直し）

- 001 では「コマンドは1回で終わり常駐しない」ことを流量の制限の前提にしていた。Web ではサーバーが動き続けるので、次のようにする。
  - 外部サービスへの要求は、サービスごとに1つのミューテックスで直列にする。カーリル用（所蔵チェック・図書館検索・図書館の登録で共有）、
    NDL サーチ用（書誌検索・本の登録で共有）、holidays-jp 用の3つ。
    同時に2つの検索が来たら、後のものは前のものが終わるまで待つ。後のものは30分のキャッシュを使える。
    ほかの要求を待つあいだも、カーリルへの問い合わせ全体の8秒の上限（001 R7）は、実際に問い合わせを始めてから数える。
  - 1回の要求あたりの上限とキャッシュは 001 R9 のとおり。
  - 利用者は1人で、検索は画面を開いたときと「更新」の操作のときだけ行う。カーリルの1時間1,000ブックリクエストの上限には、
    通常の使い方では届かない。そのため、1時間あたりの回数を数える仕組みは作らない（001 と同じ判断）。
- カーリルの1セッション100書籍リクエストの上限（001 R10「残っている対応」、issue #7）は、本機能でも変わらない。
  想定の規模（本5冊 × 10システム = 50）では当たらないので、本機能の範囲には含めない。
- 出典表示（カーリルへのリンク、NDL サーチの CC BY のクレジット、holidays-jp）は、API で返して画面に表示する。
- 要確認: カーリルのアプリケーションキーに、呼び出し元（IP アドレスや Referer）の制限があるか。
  サーバーから呼び出すので、制限があれば Cloud Run から呼べるように設定する。デプロイ前に開発者ダッシュボードで確かめる（quickstart 手順 4）。

## W10. HTTPS（FR-119）

- Cloud Run の `*.run.app` の URL は HTTPS だけを受け付ける（HTTP は HTTPS へリダイレクトされる）。証明書の管理は要らない。
- サーバーはすべての応答に `Strict-Transport-Security: max-age=31536000` を付ける。セッション Cookie には `Secure` を付ける。
- ローカルでの確認は `http://localhost` で行う。Chrome・Firefox は localhost を安全な接続として扱うので、`Secure` の Cookie も使える。
  Safari（WebKit）は `http://localhost` で `Secure` の Cookie を保存しないため、ローカルではログインできない（quickstart 手順 3 の確認結果、2026-11-06）。
  開発のためだけに `Secure` を外す分岐は入れない（本番の安全に関わる設定を、開発の都合で変えないため）。Safari では本番（HTTPS）で確かめる。

## W11. ログ（spec の Outstanding「運用の監視」）

- サーバーは、1要求ごとに「時刻・メソッド・パス・状態コード・処理時間」を標準出力に1行で書く（Cloud Logging に集まる）。
- メモ、書名の検索語、Cookie、トークン、メールアドレスはログに書かない（Constitution「個人情報」）。
- 外部サービスのエラーは、001 と同じくアプリケーションキーを伏せて書く。
- 指標やトレースの仕組みは作らない（原則 I）。

## W12. 本人確認が切れたときの入力の保護（spec Edge Cases）

- 画面は、保存の要求に `401` が返ったら、入力中の内容を `sessionStorage` に退避してから再ログインを案内する。
  ログイン後に同じ画面に戻ったら、退避した内容を入力欄に戻す。
- `sessionStorage` に置くのは入力中の1件だけで、戻したら消す。

## W13. デプロイの方法

- **Decision**:
  - 最初は手元から `gcloud run deploy --source .` を手作業で実行する（quickstart 手順 4）。
  - 手作業で一度デプロイして手順が固まったら（tasks.md T057 のあと）、自動デプロイを作る。
    - きっかけ: `main` への push（PR のマージ）
    - 仕組み: GitHub Actions。`make check` が通ったときだけデプロイする（Constitution の品質ゲート）
    - GitHub から Google Cloud への認証: Workload Identity 連携。サービスアカウントの鍵は作らない
    - デプロイの設定: ワークフローのファイルに quickstart 手順 4 と同じ `gcloud run deploy` のコマンドを書く
- **Rationale**: 手順が固まる前に自動にすると、ワークフローと quickstart の両方を直し続けることになる。
  Workload Identity 連携なら、長く有効な鍵を GitHub に置かずに済む。
- **Alternatives considered**:
  - Cloud Build のトリガー: テストとデプロイが別の場所で動き、設定の一部が Google Cloud 側に残る。
  - サービスアカウントの鍵を GitHub Secrets に置く: 鍵の漏洩と更新の管理が必要になる。
  - `service.yaml` で宣言する: 設定項目が少なく、コマンドで足りる。
- 自動デプロイにすると、利用者の知らないうちにデプロイが走るため、W3「デプロイ中の例外」を見直す。
