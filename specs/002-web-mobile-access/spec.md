# Feature Specification: スマートフォンのブラウザから使える libread（Web 化）

**Feature Branch**: `002-web-mobile-access`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "libread を Web 化する。スマホのブラウザで見られる画面を作り、クラウドで実行する。利用者は本人1人のまま。フロントエンドは Vite + React で、簡単かつ動的な実装にも対応できるようにしたい。"

## 背景

001 で、PC のターミナルから「今日読める図書館」を調べる CLI を作った（FR-015）。
しかし、どの図書館へ行くかを決めるのは多くの場合、外出前や外出先であり、手元にあるのはスマートフォンである。
本機能では、001 と同じ判定・同じ情報を、スマートフォンのブラウザから確認・操作できるようにする。
サービスは常時インターネットから到達できる場所（クラウド）で動かし、PC を起動していなくても使えるようにする。
利用者は 001 と同じく本人1人である。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - スマートフォンで今日読める図書館を確認する (Priority: P1)

利用者は外出前や外出先で、スマートフォンのブラウザから libread の画面を開く。
画面を開くと、読みかけの本すべてについて、001 と同じ基準で「今日読める図書館」と「今日は読めない図書館（理由つき）」が表示される。
本を1冊選んで、その本だけを調べ直すこともできる。

**Why this priority**: Web 化の目的そのもの。これだけで「PC がない場所でも今日行く館を決められる」という価値が出る。
本や図書館の登録は、001 の CLI から取り込んだデータ（FR-118）を使えば検証できる。

**Independent Test**: 読みかけの本と利用図書館・開館スケジュールが登録済みの状態で、スマートフォン幅の画面から開き、
001 の受け入れシナリオ（User Story 1）と同じ結果が、同じ順序・同じ理由・同じ出典表示で表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 利用図書館 A（今日開館・在架）、B（今日休館）、C（今日開館・貸出中）が登録済み,
   **When** スマートフォンのブラウザで画面を開く,
   **Then** A が「今日読める図書館」に、B が「休館」、C が「貸出中」として「今日は読めない図書館」に表示される。
2. **Given** 読める館がある,
   **When** 結果を表示する,
   **Then** 各館の今日の開館・閉館時刻、所蔵状況の取得元と取得日時、開館情報が利用者入力である旨と最終更新日、
   本ごとの所蔵状況の取得元のページへのリンクが表示される。
3. **Given** 所蔵状況の取得に時間がかかっている,
   **When** 画面を開いた直後,
   **Then** 画面は取得中であることを表示し、取得が終わると再読み込みの操作なしに結果へ切り替わる。
4. **Given** 結果を表示してから時間がたった,
   **When** 利用者が「更新」を操作する,
   **Then** その時点の時刻で判定し直した結果が表示され、表示中の基準時刻も更新される。
5. **Given** 読みかけの本が複数ある,
   **When** 1冊を選ぶ,
   **Then** その本だけを対象にした結果が表示される。

---

### User Story 2 - スマートフォンで読みかけの本とメモを管理する (Priority: P2)

利用者は館内で本を読み終えたとき、その場でスマートフォンから読んだ位置のメモを書き換える。
新しく読み始めた本を書名・著者・出版社・ISBN で探して登録したり、読み終えた本を一覧から外したりもできる。

**Why this priority**: メモの更新は館内で読み終えた直後に行うのが自然で、PC を待たずにできることの価値が大きい。
ただし P1 の確認は既存データだけで成り立つため、P2 とする。

**Independent Test**: スマートフォン幅の画面で本を探して登録し、メモを編集・消去し、本を外す。
そのたびに一覧と P1 の検索対象が変わることを確認する。

**Acceptance Scenarios**:

1. **Given** 本が未登録,
   **When** 書名と著者で探し、候補から1冊を選んで登録する,
   **Then** 読みかけの本の一覧に表示され、P1 の検索対象になる。
2. **Given** 読みかけの本が登録済み,
   **When** メモを「p.180まで」に書き換えて保存する,
   **Then** 一覧に新しいメモが表示され、画面を開き直しても保持されている。
3. **Given** 読みかけの本が登録済み,
   **When** 一覧から外す操作をし、確認に同意する,
   **Then** 一覧から消え、P1 の検索対象から外れる。
4. **Given** 書名の検索で候補が多い,
   **When** 著者・出版社で絞り込む,
   **Then** 条件に合う候補だけが表示される。

---

### User Story 3 - スマートフォンで利用図書館と開館情報を管理する (Priority: P3)

利用者は、図書館のお知らせで臨時休館を知ったとき、その場でスマートフォンから臨時休館期間を入力する。
利用図書館の追加・削除、曜日ごとの開館時間と祝日の扱いの入力も、画面から行える。

**Why this priority**: 開館情報の正しさは判定の信頼性に直結するが、更新の頻度は低く、P1・P2 より後でよい。

**Independent Test**: 図書館を探して追加し、開館スケジュールと臨時休館期間を入力・削除し、P1 の判定がその通りに変わることを確認する。

**Acceptance Scenarios**:

1. **Given** 利用図書館が未登録,
   **When** 都道府県を選び、市区町村・館名で絞り込んで1館を追加する,
   **Then** 利用図書館の一覧に表示され、「開館情報未入力」として P1 の結果に現れる。
2. **Given** 利用図書館 A が登録済み,
   **When** 曜日ごとの開館時間と祝日の扱いを入力して保存する,
   **Then** 以降の P1 の判定は入力内容に従い、開館情報の最終更新日が今日になる。
3. **Given** 利用図書館 A が登録済み,
   **When** 今日を含む臨時休館期間を入力する,
   **Then** P1 の結果で A は「休館」になる。
4. **Given** 臨時休館期間が登録済み,
   **When** その期間を削除する,
   **Then** P1 の判定は通常の開館スケジュールに戻る。

---

### Edge Cases

- 本人以外がサービスの URL を知ってアクセスした場合（本人以外の Google アカウントでログインした場合を含む）: 本人であることを確認できるまで、読みかけの本・メモ・利用図書館を含む一切の利用者データを表示せず、変更も受け付けない。
- 本人であることの確認が一定期間切れた場合: 確認をやり直すまでデータを表示しない。確認のやり直しで入力途中のメモが失われないよう、保存前に確認切れを知らせる。
- 通信が途中で切れた・電波が弱い場合: 取得できなかったことを表示し、古い結果を最新の結果として表示しない。以前の結果を表示する場合は、その基準時刻を明示する。
- 画面を開いたまま日付が変わった・閉館時刻を過ぎた場合: 表示中の結果の基準時刻を常に表示し、「更新」で判定し直せるようにする。基準時刻から30分を超えた結果には「古い情報」と明示する。
- 所蔵状況の取得元への問い合わせ上限に近い場合: 001 と同じく30分以内の取得結果を使い、上限を超える問い合わせを行わない。上限のために取得できない本は「不明」とする。
- 2つの端末（スマートフォンと PC など）でほぼ同時に同じ本のメモを編集した場合: 後から保存した内容で上書きするが、片方の保存で他のデータ（他の本・図書館）が失われてはならない。
- 画面の幅が狭い（スマートフォンを縦に持った状態）場合: 横スクロールなしで館名・状態・時刻が読める。
- 利用図書館または読みかけの本が1件も登録されていない場合: 001 と同じく、検索の前に登録を促し、その画面への導線を示す。
- サービスがしばらく使われず停止状態から起動する場合: 起動に時間がかかっても、取得中であることを表示し、エラーと誤認させない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-101**: 利用者は、スマートフォンのブラウザから、001 の FR-001〜FR-008・FR-017 と同じ基準・同じ表示内容（理由、取得元、取得日時、開館情報の最終更新日、館の並び順、取得元へのリンク、出典表示）で「今日読める図書館」を確認できなければならない。
- **FR-102**: 判定の基準は 001 と同一でなければならない。001 の受け入れシナリオと同じデータ・同じ時刻に対して、Web の画面は 001 の CLI と同じ結果を表示しなければならない。
- **FR-103**: 「今日」と現在時刻は、サービスが動く場所や端末の設定にかかわらず、日本時間で判定しなければならない。
- **FR-104**: 画面は、所蔵状況の取得中であることを表示し、取得が終わったら利用者の再読み込み操作なしに結果を表示しなければならない。
- **FR-105**: 画面には結果の基準時刻を常に表示し、利用者が「更新」を操作するとその時点で判定し直さなければならない。基準時刻から30分を超えた結果は「古い情報」と明示しなければならない。
- **FR-106**: 利用者は、スマートフォンのブラウザから、001 の FR-009・FR-010 と同じく、本を探して読みかけの本として登録・削除し、メモを保存・編集・消去できなければならない。
- **FR-107**: 利用者は、スマートフォンのブラウザから、001 の FR-011・FR-016 と同じく、利用図書館の登録・削除、開館スケジュールの入力・編集、臨時休館期間の追加・削除を行えなければならない。
- **FR-108**: 削除の操作（読みかけの本・利用図書館・臨時休館期間）は、誤操作を防ぐため実行前に確認を求めなければならない。
- **FR-109**: サービスはクラウド上で常時到達可能な状態で動き、利用者の PC が起動していなくても、FR-101・FR-106・FR-107 のすべてを利用できなければならない。
- **FR-110**: 利用者は本人1人とし、利用者登録の画面は設けない。本人の確認は Google アカウントでのログインで行い、あらかじめ設定した本人の Google アカウント1つだけを許可する。それ以外のアカウントでログインした場合は、本人でないものとして扱う。本人であることを確認できない相手には、利用者データの表示・変更・外部サービスへの問い合わせを一切行わせてはならない。
  確認できない相手への応答から、利用者データの有無（本や図書館が登録されているかどうか）が分かってはならない。
- **FR-111**: 本人の確認は、スマートフォンで毎回長い入力をしなくて済むよう、一度確認した端末では一定期間（既定30日）確認を省略できなければならない。利用者は、確認済みのすべての端末の確認を取り消せなければならない。
- **FR-112**: 利用者データ（読みかけの本・メモ・利用図書館・開館スケジュール・臨時休館期間）はクラウド上に保存し、サービスの再起動・更新後も保持されなければならない。
- **FR-113**: 外部サービスへの秘密情報（所蔵状況の取得元のアプリケーションキーなど）は、画面や端末側に渡してはならない。
  外部サービスへの問い合わせはサービス側から行い、端末から直接行ってはならない。
- **FR-114**: 外部サービスに送る情報は、001 と同じく ISBN、図書館システムID、検索語、年に限り、メモは送ってはならない。
- **FR-115**: 画面は、幅 360px 程度のスマートフォンの縦向きで、横スクロールなしに主要な情報（館名・状態・開館時刻・本の書名）を読めなければならない。PC のブラウザでも利用できなければならない。
- **FR-116**: 通信に失敗した場合は、失敗したことと再試行の方法を表示しなければならない。取得に失敗した所蔵状況を最新の情報として表示してはならない。
- **FR-117**: 001 の CLI は廃止し、本機能の Web に一本化する。PC からも Web の画面を使う。
- **FR-118**: 利用者は、001 の CLI で使っていた手元のデータ（読みかけの本・メモ・利用図書館・開館スケジュール・臨時休館期間）を、一度だけ Web に取り込めなければならない。
  取り込みの前後で件数と内容が一致し、取り込みに失敗した場合はクラウド上のデータを変更してはならない。
- **FR-119**: サービスは、暗号化された通信だけを受け付けなければならない。暗号化されていない通信で利用者データや本人確認の情報をやりとりしてはならない。

### Key Entities

001 のエンティティ（図書館、利用図書館、本、読みかけの本、所蔵状況、開館スケジュール、臨時休館期間）をそのまま使う。本機能で次を加える。

- **確認済み端末**: 本人であることを確認したブラウザ。確認した日時と有効期限を持つ。利用者が一括で取り消せる。
- **検索結果の表示**: ある基準時刻に判定した結果。基準時刻、館ごとの判定、本ごとの所蔵状況（取得元・取得日時つき）を持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 利用者は、スマートフォンでホーム画面などから libread を開いて「今日どの館で読めるか」を知るまでを、本人確認済みの端末で20秒以内に完了できる。
- **SC-102**: 利用図書館10館・読みかけの本5冊のすべてを一度に検索しても、画面を開いてから結果が表示されるまで10秒以内（サービスが停止状態から起動する場合を除く）。
- **SC-103**: 001 の受け入れシナリオと同じデータ・同じ基準時刻に対して、Web の画面の「読める」館の集合・並び順・理由が 001 の CLI の結果と100%一致する。
- **SC-104**: 本人確認をしていない端末から、利用者データが1件も読み取れない・変更できず、登録の有無も分からない。
- **SC-105**: 状態を確定できない館が「読める」と表示される件数が0件である（001 SC-004 を Web でも維持）。
- **SC-106**: 利用者は、館内でスマートフォンからメモの更新を30秒以内に完了できる。
- **SC-107**: サービスの再起動・更新の前後で、利用者データが1件も失われない。
- **SC-108**: 001 の CLI の手元のデータを取り込んだとき、読みかけの本・メモ・利用図書館・開館スケジュール・臨時休館期間が1件も欠けず、内容も一致する。

## Assumptions

- 利用者は本人1人のまま（001 FR-014 を維持）。複数利用者・共有・公開は範囲外とする。
- 想定する端末は、利用者のスマートフォンの標準ブラウザ（最新版）と PC のブラウザ。スマートフォン向けアプリのストア配布は範囲外とする。
- 通知（プッシュ通知・メール）、オフラインでの利用、ホーム画面へのアプリとしての追加への特別な対応は範囲外とする。ブラウザのブックマーク・ホーム画面への追加で開ければよい。
- 判定の基準・所蔵状況の取得元・鮮度の許容範囲（30分）・外部サービスの利用条件とレート制限は 001 のものを引き継ぐ。
  利用者が1人なので、問い合わせ量は 001 と同程度とみなす。
- 本人の確認は Google アカウントでのログインに頼る（FR-110）。Google のログインが使えない間は libread も使えなくなることを受け入れる。
- サービスの運用費は個人で負担できる範囲（無料枠または月数百円程度）に収めることを目標とし、使われていない間は停止してもよい（SC-102 の例外）。
- 利用者の要望として、画面は今後の操作性の改善（画面の一部だけの更新、取得状況の逐次表示など）にも対応しやすい作りにする。
  利用者は画面の構築に Vite + React を使うことを指定している。これは計画（plan）での技術選定の前提とする。
  Constitution 1.1.0 で、サーバーは Go、ブラウザで動く画面は TypeScript（React、Vite）と定めた。
  「読める」の判定はサーバー側だけで行い、画面は判定結果を表示する（Constitution 原則 IV）。
- 「今日」は日本時間の暦日とする（001 から変更なし）。
- 001 の CLI は本機能の完成後に廃止する（FR-117）。CLI の手元のデータは一度だけ取り込み（FR-118）、以後は Web のデータだけを使う。

## Clarifications

### Session 2026-11-04

- Q: Web 化した後、PC の CLI をどう扱うか？ → A: CLI は廃止して Web に一本化する。手元のデータは一度だけ取り込む
- Q: 本人であることを確かめる方法は、どれにするか？ → A: Google アカウントでログインし、本人のアカウント1つだけを許可する
